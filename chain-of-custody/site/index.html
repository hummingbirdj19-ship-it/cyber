Chain of Custody
How it works Setup Demo Integrate Troubleshooting Reference
Hackurity 2026 · Problem statement 6

Tamper-evident logs for any platform

Chain of Custody sits next to an existing platform, chains every event it records, and pins the chain on a second machine the attacker cannot touch. If an admin edits, deletes, reorders or truncates the logs, the verifier says so and names the attack.

Docker only: no Python install Windows, macOS, Linux (Intel and Apple silicon) Same code, one profile per platform

How it works

Three parts. The sidecar and verifier run beside the platform; the witness runs on a different laptop.

1

Chain

The sidecar reads each event the platform records (from a spool file) and links it to the previous one with SHA-256. Change one byte of an old event and every later link breaks.

2

Pin

Every 30 seconds it sends a signed heartbeat (Ed25519) with the newest entry's hash to the witness, plus signed Merkle checkpoints. The witness only ever appends.

3

Verify

The verifier recomputes the chain and compares it with what the witness saw. It prints one JSON verdict list: clean, or which attack happened and where.

What the verifier tells you

Exit code 0 = clean, 1 = tampering found, 2 = the check itself failed (never a false "clean").

VerdictWhat the attacker didNeeds the witness?
EDITChanged a field of a stored entry (or swapped two entries)No
CHAIN_BREAKAn entry no longer points at the one before itNo
SEQ_GAPDeleted entries from the middle (the missing range is reported)No
CHECKPOINT_MISMATCHRewrote and re-chained history that a signed checkpoint already coveredNo
BAD_CHECKPOINT_SIGNATUREForged or altered a checkpointNo
TRUNCATIONDeleted the newest entriesYes
FORKRewrote the whole chain, even re-signed with the stolen local keyYes
SILENCEStopped the sidecar or cut it off: no heartbeat for over 75 sYes

What we assume, and the limits

Trust model

The attacker is admin on the platform laptop: they can edit the sidecar database, the spool file and read the node's private key.

They cannot touch the witness laptop. That is why the witness catches a full rewrite even when it is re-signed with the stolen key.

Limits, stated plainly

The defence proves logs were not changed after they were recorded. It cannot prove the platform told the truth in the first place.

The newest ~32 s of events (one heartbeat interval plus the send timeout) are not yet pinned and can be removed without a witness verdict.

Setup: two laptops

Each laptop needs Docker and two small files from the repo. No clone, no Python. The images download themselves from GitHub Container Registry.

0. Before you start (both laptops)

  1. Install Docker Desktop and start it.

    From docker.com, default options. Wait for "Engine running", then check:

    docker run --rm hello-world

    Expected: Hello from Docker! (on Linux, Docker Engine works too.)

  2. Put both laptops on the same Wi-Fi or hotspot.

    Keep the clocks on automatic time. Clock drift causes false alarms.

  3. Work in a folder outside OneDrive, Dropbox or iCloud.

    The platform laptop keeps a private key and a live database there; a sync client would upload the key and can lock the database.

1. Witness laptop

  1. Make a folder and download two files.

    mkdir C:\coc-witness; cd C:\coc-witness
$base = "https://raw.githubusercontent.com/JeevikaS-19/cybersec_hackathon/main/chain-of-custody"
Invoke-WebRequest -UseBasicParsing "$base/witness-compose.yml" -OutFile witness-compose.yml
Invoke-WebRequest -UseBasicParsing "$base/coc.ps1" -OutFile coc.ps1
Set-ExecutionPolicy -Scope Process Bypass

    The last line lets this PowerShell window run coc.ps1. No admin needed; it ends when you close the window.

    mkdir -p ~/coc-witness && cd ~/coc-witness
base=https://raw.githubusercontent.com/JeevikaS-19/cybersec_hackathon/main/chain-of-custody
curl -fsSL -O "$base/witness-compose.yml" -O "$base/coc.sh"
chmod +x coc.sh

  2. Trust the platform laptop's key.

    Use the exact coc trust line that coc init printed on the platform laptop (step 2.1).

    .\coc.ps1 trust node-1 <64-character public key>
    ./coc.sh trust node-1 <64-character public key>

    Expected: [CREATED] witness_nodes.toml: node-1 is trusted

  3. Start the witness.

    docker compose -f witness-compose.yml up -d

    Check with docker logs chain-of-custody-witness: SILENCE after 75.0s without a heartbeat, then "Uvicorn running".

  4. Open port 8800 and note this laptop's IP.

    # In PowerShell "Run as administrator":
New-NetFirewallRule -DisplayName "Chain of Custody witness" -Direction Inbound -Protocol TCP -LocalPort 8800 -Action Allow
ipconfig   # IPv4 Address of the Wi-Fi adapter
    ipconfig getifaddr en0      # macOS
hostname -I                 # Linux (open 8800 in ufw/firewalld if enabled)

2. Platform laptop

  1. Make a folder, download two files, run coc init.

    Replace WITNESS-IP with the witness laptop's address.

    mkdir C:\coc-platform; cd C:\coc-platform
$base = "https://raw.githubusercontent.com/JeevikaS-19/cybersec_hackathon/main/chain-of-custody"
Invoke-WebRequest -UseBasicParsing "$base/sidecar-compose.yml" -OutFile sidecar-compose.yml
Invoke-WebRequest -UseBasicParsing "$base/coc.ps1" -OutFile coc.ps1
Set-ExecutionPolicy -Scope Process Bypass
.\coc.ps1 init --witness-url http://WITNESS-IP:8800
    mkdir -p ~/coc-platform && cd ~/coc-platform
base=https://raw.githubusercontent.com/JeevikaS-19/cybersec_hackathon/main/chain-of-custody
curl -fsSL -O "$base/sidecar-compose.yml" -O "$base/coc.sh"
chmod +x coc.sh
./coc.sh init --witness-url http://WITNESS-IP:8800

    It creates config.toml, the key pair in data/, and prints coc trust node-1 …. Send that line to the witness laptop (step 1.2).

  2. Start the sidecar.

    docker compose -f sidecar-compose.yml up -d

    The platform writes its events to spool/events.jsonl in this folder (or set SPOOL_DIR to its spool folder before up).

  3. Check everything.

    .\coc.ps1 check
    ./coc.sh check

    One line per layer. PASS everywhere, or WARN for an empty spool or before the first heartbeat (30 s). Exit 0. Nothing is changed by a check.

  4. Verify the log.

    .\coc.ps1 verify --witness http://WITNESS-IP:8800 --node-id node-1
    ./coc.sh verify --witness http://WITNESS-IP:8800 --node-id node-1

    Expected: {"clean": true, "checked_entries": N, "verdicts": []}

Rehearse on one laptop first

Do steps 1 and 2 in two different folders on the same laptop, and use --witness-url http://localhost:8800. Inside the containers, localhost is translated to the host machine automatically (coc check prints a NOTE saying so), so this works exactly like two laptops.

Demo script

Run on the platform laptop after setup, with 200 test events in and a clean verify. Each attack is what an admin with database access could do; each verify adds the new verdict. Wait 45 s after the events go in so a heartbeat has pinned them.

Shortcut

The commands below are for Windows. On macOS/Linux, replace .\coc.ps1 with ./coc.sh and "${PWD}:/work" with "$PWD":/work.

  1. Baseline: clean.

    .\coc.ps1 verify --witness http://WITNESS-IP:8800 --node-id node-1

    clean: true 200 entries, exit 0.

  2. Attack 1: quietly change who did something (entry 42).

    docker run --rm -v "${PWD}:/work" -w /work ghcr.io/jeevikas-19/coc-sidecar:latest python -c "import sqlite3; c = sqlite3.connect('data/sidecar.db'); c.execute('UPDATE entries SET actor = ? WHERE seq = 42', ('mallory',)); c.commit()"

    Verify again: EDIT at seq 42, exit 1.

  3. Attack 2: delete an embarrassing entry (entry 120).

    docker run --rm -v "${PWD}:/work" -w /work ghcr.io/jeevikas-19/coc-sidecar:latest python -c "import sqlite3; c = sqlite3.connect('data/sidecar.db'); c.execute('DELETE FROM entries WHERE seq = 120'); c.commit()"

    Verify again: adds SEQ_GAP at 120 (the hole), plus the broken link and the checkpoint that no longer matches.

  4. Attack 3: cut off the newest events (190 onward).

    docker run --rm -v "${PWD}:/work" -w /work ghcr.io/jeevikas-19/coc-sidecar:latest python -c "import sqlite3; c = sqlite3.connect('data/sidecar.db'); c.execute('DELETE FROM entries WHERE seq >= 190'); c.commit()"

    Wait 35 s for the next heartbeat, verify again: adds TRUNCATION. Locally the tail looks fine; only the witness knows there were 200.

  5. Attack 4: switch the logging off.

    docker compose -f sidecar-compose.yml stop sidecar

    Wait 2 minutes, verify again: adds SILENCE. Then docker compose -f sidecar-compose.yml start sidecar.

Reset after the demo

The witness remembers every alert (that is the point), so a fresh start clears both sides. The keys stay, so no new coc trust is needed.

# platform laptop
docker compose -f sidecar-compose.yml down
Remove-Item data\sidecar.db*, spool\events.jsonl     # macOS/Linux: rm data/sidecar.db* spool/events.jsonl
# witness laptop
docker compose -f witness-compose.yml down -v
docker compose -f witness-compose.yml up -d
The full-rewrite attack (FORK)

Rewriting the whole chain and re-signing it with the stolen key is covered by the automated self-test, which runs five attacks plus a clean baseline. From a clone of the repo: python -m tests.test_tampering.

| Clean baseline      | CLEAN      | CLEAN      | PASS |
| Edit in place       | EDIT       | EDIT       | PASS |
| Delete in middle    | SEQ_GAP    | SEQ_GAP    | PASS |
| Truncate tail       | TRUNCATION | TRUNCATION | PASS |
| Reorder two entries | EDIT       | EDIT       | PASS |
| Fork and rewrite    | FORK       | FORK       | PASS |

Plug in a platform

Protecting a new platform means writing a profile, never changing the defence code. The interface is CONTRACT.md; this is the short version.

The event format (one JSON object per line in the spool)

{"source": "app", "ts": "2026-10-12T09:15:30Z", "actor": "asha", "event_type": "login_success", "details": {"ip": "10.0.0.5"}}
FieldRule
sourceapp, db or host
tsUTC, seconds, trailing Z: 2026-10-12T09:15:30Z
actoruser or account name, unknown if none
event_typesnake_case, e.g. transaction_created; optionally limited by the profile's allow-list
detailssmall object; no floats anywhere (money as a string), no passwords or tokens

The spool is append-only, one writer, one line per write, \n line endings. Anything that breaks a rule is rejected, never silently accepted. Check a spool before going live:

docker run --rm -v "${PWD}:/work" -w /work ghcr.io/jeevikas-19/coc-sidecar:latest python -P -m tools.validate_spool spool/events.jsonl --config config.toml

The profile (config.toml, written by coc init)

SectionKeysNotes
[profile]name, event_typesLabel for humans; optional allow-list (empty = any snake_case name)
[node]node_idLetters, digits, . _ -, up to 64; must match what the witness trusts
[paths]spool_path, db_path, key pathsKeep relative, under spool/ and data/
[checkpoint]every_n, every_sSigned checkpoint every 50 entries or 60 s
[heartbeat]interval_s, witness_url30 s; the witness laptop's address. Witness COC_INTERVAL_S must match

Unknown keys and wrong types are errors with the key path (heartbeat.intervl_s: unknown key), so a typo never goes unnoticed. coc check reports them.

Troubleshooting

Every one of these happened to us at least once.

"running scripts is disabled on this system" (Windows)

Windows blocks .ps1 files by default, and downloaded ones even more. Run Set-ExecutionPolicy -Scope Process Bypass in that PowerShell window first. It needs no admin and resets when the window closes.

Docker Desktop will not start

"Virtualization not enabled": Task Manager → Performance → CPU must show Virtualization: Enabled; if not, turn on Intel VT-x / AMD SVM in the BIOS.

"WSL 2 is not installed": in an admin PowerShell run wsl --install, then restart.

coc check: FAIL witness unreachable

Work through the checklist it prints: the witness laptop's IP and port, port 8800 open in its firewall, both laptops on the same network, the witness container running (docker ps on the witness laptop). From the platform laptop, Test-NetConnection WITNESS-IP -Port 8800 (Windows) or curl http://WITNESS-IP:8800/heartbeats?node_id=node-1 should answer.

WARN reachable, but no heartbeats yet

Normal for the first 30 s after up. If it stays: the witness does not trust this node. Run the coc trust line from coc init on the witness laptop, then docker compose -f witness-compose.yml restart witness.

The witness exits: "nodes_file … is a directory"

Docker created a folder because witness_nodes.toml did not exist when the witness started. Delete the folder, run coc trust, start again.

The witness exits: TOML or "byte-order mark" error

The trust file was edited in Notepad and saved as "UTF-8 with BOM". Delete it and recreate it with coc trust.

Verify says SILENCE, but nothing was attacked

The sidecar was stopped for over 75 s, or the laptop slept, or the network dropped. The witness records it and keeps it: that is correct. For a fresh demo, use the reset in the demo section.

If it happens constantly: the witness COC_INTERVAL_S differs from the profile's interval_s. They must be equal.

Two commands pasted on one line

Pasting verify and echo together makes the second an argument of the first ("unrecognized arguments"). Run one command per line.

coc init says a different key is trusted for this node

The trust file already holds an older key for that node id. Deliberate reset: coc init --force (refused while a sidecar database exists) or coc trust … --replace on the witness laptop.
